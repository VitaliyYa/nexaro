# Архитектурные решения (Architecture Decision Records - ADR)

В этом документе фиксируются ключевые технические и архитектурные решения платформы SmartRent.

## ADR 1: Архитектура сети IoT (MQTT Connections)
**Контекст:** Квартиры (Edge-узлы) подключены к интернету через разных провайдеров, часто находятся за NAT, не имеют статических IP-адресов.
**Решение:** Использовать MQTT-брокер (Eclipse Mosquitto) на центральном VPS, доступный по порту 8883 (TLS). Локальные контроллеры (HAOS) будут выступать инициаторами подключения (исходящий трафик).
**Обоснование:** Исключает необходимость проброса портов, настройки DDNS или туннелей на локальных роутерах. Гарантирует безопасность благодаря TLS и жестко ограниченным ACL для каждой квартиры.

## ADR 2: Управление состоянием (State Management & UI Pattern)
**Контекст:** Команды, отправляемые IoT-устройствам, могут не выполниться из-за потери связи или аппаратного сбоя.
**Решение:** 
1. Разделение MQTT топиков на `.../set` (для команд) и `.../state` (для подтвержденных статусов) с флагом `retain: true`.
2. UI-паттерн `optimistic: false`: элементы интерфейса (тумблеры) не переключаются мгновенно, а переходят в состояние загрузки, ожидая физического подтверждения от устройства (`state`).
**Обоснование:** Исключает рассинхронизацию между реальным состоянием устройства и интерфейсом пользователя.

## ADR 3: Технологический стек Frontend
**Контекст:** Выбор фреймворка для разработки личного кабинета пользователя.
**Решение:** Vue 3 + Vite + Pinia (Single Page Application). Отказ от SSR (например, Nuxt.js).
**Обоснование:** Экономия серверных ресурсов. Поскольку приложение является закрытой панелью управления (B2B SaaS), SEO-оптимизация не требуется, а SSR является избыточным усложнением инфраструктуры.

## ADR 4: Интеграция умных замков (TTLock)
**Контекст:** Определение способа связи с замками TTLock.
**Решение:** Основной фокус на **локальную интеграцию** в HAOS. При этом в архитектуру бэкенда закладывается возможность работы через официальный Cloud API TTLock.
**Обоснование:** Локальная интеграция обеспечивает высокую надежность и отказоустойчивость при проблемах с интернетом. Поддержка Cloud API в будущем позволит легко подключать клиентов, у которых уже настроено облачное управление замками.

## ADR 5: Связь Frontend -> Realtime Обновления Состояний Устройств
**Контекст:** Как клиентский Frontend получает мгновенные подтверждения физического переключения устройств (`state`) для соблюдения паттерна `optimistic: false`.
**Статус:** Принято.
**Решение:** 
1. Использовать **Supabase Realtime** (`postgres_changes` на таблице `devices`).
2. Применять паттерн **Fetch-then-Subscribe**: при монтировании дашборда объекта сначала выполняется первичный REST-запрос актуальных устройств (`GET /properties/{id}/devices`), после чего открывается подписка на канал `supabase.channel('property-devices-{id}')` с фильтром `property_id=eq.{id}`. При размонтировании (уходе со страницы) канал гарантированно отписывается.
3. Таблица журнала телеметрии `device_logs` не подписывается на Realtime во избежание лишнего трафика и читается по требованию через REST API с пагинацией.
**Обоснование:**
1. Исключает необходимость выставления порта брокера Mosquitto (9001 WSS) напрямую в браузер клиентам и генерации клиентских MQTT-токенов.
2. Безопасность и мультитенантность полностью обеспечиваются Row Level Security (RLS) Supabase на уровне JWT токена пользователя.
3. Минимальная задержка: MQTT Worker сохраняет валидированный статус в таблицу `devices`, что мгновенно триггерит репликацию PostgreSQL изменения в браузер.

## ADR 6: Динамическая аутентификация и ACL в Mosquitto через HTTP Webhook (mosquitto-go-auth)
**Контекст:** Хранение учетных данных Edge-узлов и списков контроля доступа (ACL) в статических файлах `passwd` и `acl` на диске или в репозитории несет риски утечки секретов и усложняет динамический отзыв прав.
**Решение:** Использовать плагин `mosquitto-go-auth` с HTTP бэкендом. Проверка учетных данных (`/user`), суперпользователей (`/superuser`) и прав на топики (`/acl`) делегируется FastAPI Backend'у с хранением хэшей паролей в Supabase (`mqtt_credentials`).
**Обоснование:** 
1. Полное исключение паролей и хэшей из git-репозитория и файловой системы брокера.
2. Мгновенная блокировка доступа при деактивации узла в базе данных без перезапуска Mosquitto или чтения локальных файлов.
3. Единый источник истины (SSOT) для прав доступа на уровне бизнес-логики Backend и RLS.
