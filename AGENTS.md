# Руководство для ИИ-Агентов (AGENTS.md)

Этот документ определяет операционные правила, протоколы безопасности репозитория, архитектурные ограничения и стандарты написания кода для ИИ-ассистентов и разработчиков, работающих над репозиторием **SmartRent**.

---

### Обязательный протокол рабочего процесса

#### В начале КАЖДОЙ сессии:
1. Прочитать `AGENTS.md` (этот файл), `IMPLEMENTATION_PLAN.md`, `CHANGELOG.md` и `DECISIONS.md`.
2. Если задача включает тестирование или проверку UI — прочитать `TESTING.md`.
3. Проверить текущий статус git и ветку перед изменением любых файлов.

#### Протокол выполнения для Агента ("Inspect before Edit" - Изучи перед редактированием):
Перед изменением кода:
1. Ознакомиться со всей необходимой проектной документацией.
2. Проверить текущую ветку и состояние рабочей директории (`git status`).
3. Изучить релевантные исходные файлы.
4. Изучить релевантные unit-тесты.
5. Изучить связанные архитектурные решения в `DECISIONS.md`.
6. Сравнить запрошенное изменение с планом `IMPLEMENTATION_PLAN.md`.
7. Только после этого приступать к редактированию кода.

#### Перед тем, как считать задачу или стадию завершенной:
1. Запустить полный цикл проверок (линтеры, юнит-тесты).
2. Обновить `IMPLEMENTATION_PLAN.md` — отметить выполненные шаги и зафиксировать фактическое состояние.
3. Если затронут функционал, видимый пользователю, — добавить запись в `CHANGELOG.md` (формат Keep a Changelog).
4. Если было принято, изменено или отменено архитектурное решение — обновить `DECISIONS.md` (не создавать ADR для рутинных деталей реализации).
5. Если изменились сценарии ручного или автоматизированного тестирования — обновить `TESTING.md`.
6. Проверить итоговый статус git (`git status`). Убедиться, что рабочая директория чиста (в рамках задачи) и нет потерянных файлов.
7. Не считать задачу завершенной, пока документация не будет синхронизирована с кодом.

## 1. Безопасность репозитория и протокол Git

### Правило 1: Ветка `main` только для чтения
- Ветка `main` строго **только для чтения (read-only)** для ИИ-агентов.
- **Никогда** не делайте коммиты напрямую в `main`.
- Все новые ветки для стадий или фич должны создаваться явно из `main` (например, `git checkout -b <branch-name> main`) **перед** изменением файлов.
- Никогда не создавайте ветки от произвольных или грязных веток, если об этом явно не попросил пользователь.

### Правило 2: Чистота рабочей директории
- Перед переключением веток или началом работы выполните `git status`.
- Если есть незакоммиченные изменения, не относящиеся к вашей задаче:
  - **Не** перезаписывайте, не отменяйте (`git reset --hard`), не прячьте (`git stash`) и не коммитьте их.
  - Сообщите пользователю и спросите, как действовать дальше.
- Убедитесь, что в stage (индекс) добавлены только файлы, относящиеся к текущей задаче.

### Правило 3: Иерархия (Задача → Стадия → Логический шаг → Коммит)
Стадии в `IMPLEMENTATION_PLAN.md` представляют собой крупные вехи. Работа внутри стадии должна быть разбита на логические шаги. **Никогда не делайте один монолитный коммит на всю стадию.**
Используйте общепринятые префиксы для коммитов (`feat:`, `fix:`, `test:`, `docs:`, `refactor:`, `chore:`).

### Правило 4: Строгий контроль скоупа (Никакого рефакторинга "мимоходом")
- Не выполняйте посторонний, стилистический или косметический рефакторинг за пределами текущего логического шага.
- Не трогайте работающий код, не относящийся к задаче.
- Сохраняйте существующее форматирование и комментарии, если явно не указано иное.

### Правило 5: Отклонение от плана и разрешение конфликтов
- Не изменяйте будущие стадии в `IMPLEMENTATION_PLAN.md` только потому, что вам кажется, что они должны быть другими.
- Если вы обнаружили существенное расхождение, где `IMPLEMENTATION_PLAN говорит А`, а `реальный код требует Б`:
  1. **Немедленно остановите выполнение.**
  2. **Четко сообщите пользователю о расхождении.**
  3. **Объясните технические причины и последствия.**
  4. **Предложите обновленный план.**
  5. **Дождитесь подтверждения от пользователя.**

## 2. Обзор проекта и архитектурные ограничения

**SmartRent** — это B2B SaaS платформа, управляющая устройствами IoT для краткосрочной аренды недвижимости.

### Ключевые архитектурные ограничения
- **Языковой стандарт:** Вся проектная документация (`*.md`) пишется на **Русском** языке, код и комментарии к коду пишутся на **Английском**.
- **Технологический стек:**
  - **Backend:** Python 3.14 (uv), FastAPI, paho-mqtt.
  - **Frontend:** Vue 3 (Composition API), Vite, Pinia (SPA, без SSR).
  - **Database:** Supabase (PostgreSQL) с использованием Row Level Security (RLS).
  - **Edge / IoT:** Home Assistant OS, Eclipse Mosquitto (MQTT 8883, TLS).
- **Безопасность и Приватность (Критический уровень):**
  - **MQTT Изоляция тенантов (ACL):** Каждому Edge-узлу (квартире) выдаются уникальные учетные данные для брокера. Обязательна динамическая генерация ACL-записей (например, через плагин `mosquitto-go-auth`) со строгим ограничением доступа только к своему пространству топиков: `properties/<property_id>/#`. Скомпрометированный узел не должен иметь возможности слушать или отправлять данные в чужие топики.
  - **Безопасность PIN-кодов (Смарт-замки):** Управление физическим доступом — самый чувствительный функционал. PIN-коды **никогда не логируются**, хранятся зашифрованными (encrypted at rest). Любое действие с кодами сопровождается строгим Audit Log (кто, когда, какое действие совершил). Токены и ключи TTLock API существуют только на Backend и никогда не передаются в клиентский бандл (Frontend).
  - **Supabase RLS и Service Role:** По умолчанию Backend получает токен от Frontend и выполняет запросы от лица пользователя (срабатывает RLS мультитенантности). Использование `service_role` ключа (в обход RLS) разрешено **только** для фоновых системных задач или провижининга, и эти операции должны быть физически изолированы в коде от пользовательских роутов. Смешивание `service_role` с пользовательскими запросами строго запрещено.
  - **Управление секретами (.env):** Секреты (ключи API, пароли к MQTT, Service Key Supabase) передаются исключительно через переменные окружения. Файлы `.env` никогда не коммитятся в репозиторий. В CI/CD (GitHub Actions) используются исключительно GitHub Secrets.
- **Паттерн UI (optimistic: false):**
  - Frontend не меняет состояние элементов (тумблеров) мгновенно. Вместо этого они переходят в состояние загрузки и обновляются только при получении пакета `state` из MQTT/Backend.

## 4. Протоколы и схемы данных

### Схема топиков MQTT
Пространство имен жестко стандартизировано для изоляции объектов:
- **Команда (от облака к Edge):** `properties/<property_id>/<device_type>/<device_id>/set`
- **Статус (от Edge к облаку):** `properties/<property_id>/<device_type>/<device_id>/state`

### Payload MQTT и контракты данных (SSOT)
В качестве единого источника истины (Single Source of Truth) для форматов данных используются JSON Schema, хранящиеся в директории `schemas/`.
Из этих схем должны автоматически генерироваться:
- Pydantic модели для Backend (через инструменты типа `datamodel-code-generator`).
- Типы/Интерфейсы для Frontend (через `json-schema-to-typescript` или аналоги).

Это гарантирует отсутствие рассинхронизации структур данных между IoT-устройствами, бекендом и клиентом. Для простейших устройств (вроде реле) допускается использование строковых примитивов (`ON`/`OFF`), но любые сложные структуры (состояния замка, настройки климата) обязаны иметь строго определенный контракт в `schemas/`.

### База данных (Supabase RLS)
Таблица `devices` должна содержать политику:
```sql
CREATE POLICY "Users can view own property devices"
ON devices FOR SELECT USING (
  property_id IN (SELECT id FROM properties WHERE owner_id = auth.uid())
);
```

## 5. Правила кодирования и дизайн модулей

### Правило 1: Backend (FastAPI & Python)
- Использовать строгую типизацию (Type Hints) и `Pydantic` модели для валидации всех входящих/исходящих данных.
- Разделять роутеры (API endpoints) и сервисный слой (бизнес-логика).
- Зависимости (DI) FastAPI должны использоваться для передачи сессий БД и клиентов MQTT.
- Использовать `uv` для управления зависимостями.

### Правило 2: Frontend (Vue 3)
- Использовать `<script setup>` и Composition API.
- Выносить логику общения с API и MQTT в модули Pinia (Store).
- Внедрить принцип `optimistic: false`:
  - Клик на переключатель -> `store.dispatch('toggleDevice')`
  - Переключатель получает состояние `loading = true`.
  - По факту успешного получения обновления -> состояние обновляется, `loading = false`.

### Правило 3: Edge (HAOS)
- Все автоматизации (мосты MQTT -> Служба) должны быть идемпотентными.
- Для выключателей без обратной связи использовать `toggle` паттерн на стороне HAOS, а не на клиенте (описано в экспериментах).
- Все `state` публикации от HAOS должны отправляться с флагом `retain: true`.

## 6. Команды проверки (Verification Commands)

### Backend (Python):
```bash
# Переход в директорию бекенда
cd backend

# Проверка линтером (Ruff)
uv run ruff check .
uv run ruff format --check .

# Запуск юнит-тестов
uv run pytest
```

### Frontend (Vue):
```bash
# Переход в директорию фронтенда
cd frontend

# Проверка линтером (ESLint)
npm run lint

# Запуск юнит-тестов
npm run test:unit
```
